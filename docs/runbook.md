# Runbook

## Что где живёт

| Что | Где |
|---|---|
| Источник истины по камерам и ссылкам | PostgreSQL |
| Конфигурация путей MediaMTX | производная, восстанавливается из БД за 15 с |
| Сессии панели, кэш authz, rate-limit | Redis |
| Учётные данные камер, TOTP-секреты | БД, зашифрованы ключом `secrets/app_key` |
| Токены публичных ссылок | нигде — в БД только SHA-256 |

Ключевое следствие: **перезапуск или потеря MediaMTX не требует ручных
действий**. Потеря Redis разлогинит пользователей и оборвёт открытые
просмотры, но данные не пострадают. Потеря `app_key` необратима.

```bash
docker compose ps
```


```bash
docker compose exec api python -m app.cli healthcheck
```

Состояние путей медиа-сервера:

```bash
docker compose exec mediamtx wget -qO- http://127.0.0.1:9997/v3/paths/list
```

Готовность зависимостей (изнутри сети, наружу закрыто):

```bash
docker compose exec api python -c "import httpx;print(httpx.get('http://127.0.0.1:8000/readyz').text)"
```

## Типовые ситуации

### Камера показывает «offline» или «error»

Откройте карточку камеры и нажмите **«Проверить сейчас»**. Проверка идёт до
минуты и проходит весь путь пакета, показывая, на каком шаге всё встало:

| Шаг | Что означает провал |
|-----|---------------------|
| Имя хоста | опечатка в адресе либо DNS недоступен из контейнера |
| TCP `host:port` | нет проброса на роутере камеры либо сервер не выпускают наружу |
| RTSP-соединение | камера отвечает, но поток не отдаёт — под шагом написано, почему |
| Кодеки | что реально в потоке |
| WebRTC / LL-HLS | сможет ли это показать браузер (см. следующий раздел) |
| Состояние в MediaMTX | поднят ли поток на медиа-сервере и сколько байт принято |

Под каждым упавшим шагом — подсказка, что делать. Полный вывод ffprobe
раскрывается внизу отчёта; пароль камеры в нём замаскирован, поэтому текст
можно пересылать как есть.

Отдельно:

* `401`/`Unauthorized` — сменили пароль на камере. Введите новую ссылку
  в поле «Новая RTSP-ссылка». Спецсимволы пароля кодировать вручную не нужно.
* Статус `idle` — это **не авария**: камера в режиме on-demand и её никто
  не смотрит. Соединение закрыто намеренно.

### Чёрный экран в плеере, ошибок нет

Это почти всегда кодек: соединение установилось, а декодировать нечем.
Плеер сам напишет об этом через несколько секунд («поток подключился, но
кадры не приходят»). Проверка камеры покажет то же самое явно.

H.265 (HEVC) по WebRTC не проходит в принципе, а в HLS его играет только
Safari и часть Chrome с аппаратным декодером. Лечится одним способом —
профилем «Перекодировать в H.264/Opus». В отчёте диагностики для этого есть
кнопка. Транскод стоит примерно одно ядро CPU на камеру, следите за нагрузкой.

### Видео не идёт ни в одном браузере, в плеере «WebRTC недоступен»

В панели плеера есть переключатель транспорта — **Авто / WebRTC / HLS**.
Зафиксируйте каждый по очереди: это самый быстрый способ понять, что именно
не проходит в сети зрителя. Причина отказа пишется в плашке поверх видео.

1. Проверьте, что открыты `8189/udp` **и** `8189/tcp`: `sudo ufw status`.
   TCP — это ICE-кандидат для сетей, где закрыт исходящий UDP; без него
   WebRTC там не поднимется вообще.
2. Проверьте `PUBLIC_HOST` в `.env` — именно этот адрес уходит браузеру
   в ICE-кандидатах.
3. Если работает только режим HLS — дело в сети зрителя, не в сервисе.
   Если и HLS не работает в Chrome, а плеер пишет про hls.js — библиотека
   не скачана: `bash ops/fetch-vendor.sh`.

### Потерян адрес выданной ссылки

Показать его невозможно: в БД лежит только SHA-256 от токена, а сам токен
показывается один раз при создании. На карточке камеры есть кнопка
**«Перевыпустить»** — она выдаёт новый адрес для той же ссылки. Прежний
адрес при этом перестаёт работать, а текущие зрители отключаются.

### Ссылка утекла

```bash
docker compose exec api python -m app.cli revoke-link --slug <slug>
```

Или кнопка «Отозвать» на карточке камеры. Отзыв мгновенный: кэш решения
сбрасывается, а активные WebRTC-сессии на этой камере обрываются. Зрители
с другими действующими ссылками переподключатся сами за секунду.

Кто и когда смотрел — «Журнал» → фильтр `link.viewed`.

### Пользователь потерял телефон с 2FA

Администратор: «Пользователи» → «Сбросить 2FA». Операция пишется в журнал;
до повторной настройки вход защищён только паролем, поэтому просите
настроить второй фактор сразу.

Если 2FA потерял единственный администратор, а коды восстановления не
сохранены — вход возможен только через сброс в БД:

```bash
docker compose exec postgres psql -U rtspgw -d rtspgw -c \
  "UPDATE users SET totp_enabled=false, totp_secret_enc=NULL WHERE email='admin@company.ru'"
```

### Забыт пароль

```bash
docker compose exec -it api python -m app.cli reset-password --email user@company.ru
```

### Браузер показывает ERR_SSL_PROTOCOL_ERROR

Смотрите в access-лог Caddy: если запросов на 443 там **нет вообще**, значит
соединение рвётся на TLS-рукопожатии, до HTTP. Проверить напрямую:

```bash
openssl s_client -connect <адрес>:443 -servername <адрес> </dev/null 2>&1 | head -20
```

Если с `-servername` рукопожатие проходит, а без него — нет, то Caddy не может
подобрать сертификат при отсутствии SNI. Так бывает при доступе по IP: браузер
не кладёт IP-литерал в SNI, а Caddy внутри контейнера видит только адрес
docker-сети. Лечится глобальной опцией `default_sni {$DOMAIN}` в `Caddyfile` —
она уже там; если её убрали, верните.

### Удаление и повторная установка

Для тестовых прогонов — когда нужно попробовать разные способы поднятия, не
переустанавливая систему:

```bash
sudo bash uninstall.sh --status
```

```bash
sudo bash uninstall.sh --reset -y && sudo bash install.sh
```

Уровни:

| Флаг | Что удаляет | Когда |
|---|---|---|
| `--reset` | контейнеры, базу, Redis, сертификаты | быстрый перезапуск с нуля в том же режиме |
| `--full` | + `.env`, ключ шифрования, hls.js, правила файрвола | проверить другой способ поднятия |
| `--purge` | + пакеты Docker и его репозиторий | вернуть сервер в исходное состояние |

Флаг `-y` пропускает подтверждения — для циклов. Резервные копии в
`/var/backups/rtspgw` не удаляются никогда, кроме явного `--backups`.
Правило файрвола для SSH не трогается ни при каких условиях.

**Про лимиты Let's Encrypt.** На один набор имён выдаётся не больше пяти
сертификатов в неделю. Несколько прогонов установки подряд с настоящим
доменом упрутся в этот лимит, и ждать придётся неделю. На время тестов
ставьте тестовый CA — установщик предлагает это сам, либо вручную в `.env`:

```
ACME_CA=https://acme-staging-v02.api.letsencrypt.org/directory
```

Сертификат будет недоверенным (браузер предупредит), зато лимитов нет.
Совсем без обращений наружу работает режим со своим CA (`TLS_ISSUER=internal`).

### Переезд с IP на домен (или наоборот)

Правится в `.env` и применяется перезапуском Caddy:

```bash
docker compose up -d caddy
```

| Куда переезжаем | `DOMAIN` | `TLS_ISSUER` | `PUBLIC_HOST` |
|---|---|---|---|
| На свой домен | `cam.company.ru` | почта | `cam.company.ru` |
| На sslip.io | `203-0-113-10.sslip.io` | почта | `203.0.113.10` |
| На голый IP | `203.0.113.10` | `internal` | `203.0.113.10` |

Что нужно учесть:

* **Ранее выданные публичные ссылки перестанут работать** — в них зашит старый
  адрес. Ссылки придётся создать заново и разослать.
* Сессии в панели останутся, а вот cookie привязана к домену, так что
  пользователи разлогинятся.
* При переходе на домен старый сертификат внутреннего CA можно не удалять —
  Caddy просто перестанет им пользоваться.

### MediaMTX не стартует после обновления образа

Почти всегда — незнакомый ключ в `mediamtx/mediamtx.yml`. В логе будет имя
поля. Сверьте конфиг с `mediamtx.yml` нужного тега в репозитории MediaMTX.

### Кончилось место

```bash
docker system df && docker system prune -a --volumes=false
```

Снапшоты-превью лежат в томе `snapshots`, по одному JPEG на камеру —
занимают мало. Основной рост — логи docker (ограничены 10 МБ × 5 на сервис)
и данные Prometheus (retention 30 дней).

## Ротация ключа шифрования

```bash
docker compose exec api python -m app.cli rotate-key
```

Команда перешифрует все секреты новым ключом и напечатает его. Дальше
положите новый ключ в файл и восстановите права — иначе приложение не
сможет его прочитать:

```bash
chown 10001:10001 secrets/app_key && chmod 400 secrets/app_key
docker compose restart api worker
```

Пока ключ не заменён, сервис продолжает работать на старом.

**Про права на `secrets/app_key`.** Docker монтирует файл в контейнер как
есть, вместе с владельцем и правами хоста. Процесс приложения работает под
uid 10001, поэтому файл, принадлежащий root с правами 600, он прочитать не
сможет: контейнер упадёт на старте с `Permission denied`, а compose покажет
только `container is unhealthy`.

## Восстановление из бэкапа

```bash
./ops/restore.sh /var/backups/rtspgw/rtspgw-20260902-030000.sql.gz
```

Убедитесь, что `secrets/app_key` соответствует дампу. Прогоняйте эту
процедуру на тестовом стенде хотя бы раз в полгода: непроверенный бэкап
бэкапом не является.

## Полная переустановка без потери данных

Тома `pgdata`, `redisdata`, `caddy_data`, `snapshots` переживают
`docker compose down`. Данные теряет только `down -v` — эту команду
без свежего бэкапа не выполнять.
