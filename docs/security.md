# Безопасность

## Модель угроз

От кого защищаемся:

1. **Посторонний в интернете** — сканирует порты, перебирает адреса ссылок,
   пробует форму входа.
2. **Получатель ссылки, который поделился ею дальше** — самая вероятная
   утечка на практике.
3. **Тот, кто добрался до дампа БД** — бэкап на чужом диске, доступ к
   Postgres.
4. **Сотрудник с доступом к панели, действующий за пределами полномочий.**

Не покрывается: компрометация самого хоста с правами root и физический
доступ к серверу. Против этого работают только внешние меры — SSH по ключам,
отдельная учётная запись, регулярные обновления ОС.

## TLS и режим развёртывания

Панель и медиа всегда идут по HTTPS — режима без шифрования нет намеренно:
по этому каналу ходят пароли, коды 2FA и cookie сессий.

Различаются только источники сертификата (см. [install.md](install.md)):

| Режим | Что видит зритель | Когда уместен |
|---|---|---|
| Домен + Let's Encrypt | ничего необычного | основной вариант |
| `*.sslip.io` + Let's Encrypt | ничего необычного | домена нет, IP публичный |
| IP + собственный CA | предупреждение браузера | внутренняя сеть |

Про третий режим важно понимать: шифрование там полноценное (тот же TLS 1.3),
но **аутентификации сервера для непосвящённого зрителя нет** — предупреждение
браузера означает, что подменить сервер на пути от предупреждения защищает
только внимательность пользователя. Приучать людей нажимать «всё равно
перейти» — плохая практика: ровно этим пользуются при атаках. Поэтому:

* если корневой сертификат установлен на машины зрителей — режим безопасен
  наравне с остальными;
* если ссылки уходят людям вне компании — используйте домен или sslip.io.

Cookie остаются `Secure` во всех режимах: соединение всё равно `https://`,
даже когда сертификат подписан своим CA.

## Периметр

Наружу открыты `80/tcp` (только редирект и ACME), `443/tcp`, `8189/udp` и `8189/tcp`.
`8189/tcp` — ICE-кандидат WebRTC для сетей, где закрыт исходящий UDP; медиа там
так же шифруется DTLS-SRTP, дополнительной поверхности атаки порт не добавляет.
Всё остальное — Control API MediaMTX (9997), метрики (9998), сигналинг
HLS/WebRTC (8888/8889), Postgres, Redis — слушает исключительно внутри
docker-сетей и не публикуется на хосте.

Сети разделены на три:

| Сеть | Кто | Зачем |
|---|---|---|
| `edge` | caddy, api, mediamtx | внешний трафик |
| `core` | api, worker, mediamtx | Control API, исходящий RTSP к камерам |
| `data` | api, worker, postgres, redis | хранилища, `internal: true` — без выхода в интернет |

Caddy не подключён к `core`, поэтому даже при его компрометации Control API
MediaMTX остаётся недостижим. Postgres и Redis не имеют выхода в интернет
вообще.

RTSP-сервер MediaMTX слушает только `127.0.0.1:8554` внутри своего
контейнера — он нужен единственному потребителю, локальному ffmpeg профиля
transcode. Приём потоков снаружи невозможен.

## Доступ к медиа

Ни один медиа-запрос не попадает в MediaMTX без проверки:

```
браузер → Caddy → forward_auth → /internal/authz → 200/403 → MediaMTX
```

Токен ссылки — 32 случайных байта, в БД лежит только SHA-256. Отзыв
мгновенный: списков отзыва нет, достаточно пометить строку. Токен участвует
только в первом запросе страницы просмотра; дальше действует HttpOnly-cookie,
поэтому токен не оседает в логах прокси и в заголовке Referer.

Имя пути в MediaMTX — 24 случайных символа, отдельно от slug ссылки. Даже
при ошибке в forward_auth перебрать пути нельзя.

Ограничения на ссылку: срок действия (по умолчанию сутки, а не «бессрочно»),
лимит одновременных зрителей, список разрешённых IP/CIDR, пароль.

**Известное ограничение:** установленное WebRTC-соединение идёт напрямую по
UDP и forward_auth его больше не видит. Поэтому отзыв ссылки принудительно
обрывает все WebRTC-сессии этой камеры — включая зрителей с другими
действующими ссылками. Они переподключаются автоматически за секунду.

## Панель

| Механизм | Реализация |
|---|---|
| Пароли | argon2id, 64 МБ / 3 прохода, минимум 12 символов |
| Второй фактор | TOTP с защитой от повторного использования кода, 10 одноразовых кодов восстановления |
| Сессии | серверные в Redis, cookie только с идентификатором, HttpOnly + Secure + SameSite=Lax; обычная сессия — скользящее окно 12 ч |
| «Запомнить меня» | галочка при входе продлевает сессию до 30 дней (`REMEMBER_ME_DAYS`, 0 — выключить). Предел жёсткий: активность его не сдвигает, пароль вводится минимум раз в месяц. Долгая сессия видна в профиле с датой окончания, отзывается кнопкой «Завершить остальные» и гибнет при смене или сбросе пароля |
| Фиксация сессии | идентификатор меняется после входа и после подтверждения 2FA |
| CSRF | токен в серверной сессии, поле формы или заголовок `X-CSRF-Token` |
| Перебор | лимит по IP и по логину, блокировка учётной записи на 15 минут после 10 неудач |
| Перечисление учёток | одинаковый текст ошибки и проверка хеша-заглушки для несуществующего пользователя |
| Открытые редиректы | параметр `next` принимается только как локальный путь |
| Приглашения | одноразовый токен 32 байта, в базе только его SHA-256; срок 72 ч; повторная отправка перевыпускает токен; учётная запись создаётся лишь в момент принятия |
| Подстановка заголовков письма | адрес получателя проходит проверку формата, `\r` и `\n` в заголовках отклоняются |
| Рассылка с нашего домена | не больше 30 приглашений в час и 10 проверочных писем за 10 минут на администратора |
| Настройки SMTP | меняет только администратор, пароль шифруется тем же ключом, что и креды камер, и в форму не возвращается |
| CSP | `default-src 'none'`, без `unsafe-inline` и `unsafe-eval`, nonce на каждый ответ |
| Встраивание | `X-Frame-Options: DENY` везде, кроме `/embed/*`. Cookie доступа к медиа помечена `SameSite=None; Secure` — без этого страница во встроенном iframe получала бы отказ на каждый сегмент. Сессия панели остаётся `SameSite=Lax`. Браузеры с полной блокировкой сторонних cookie (Safari, Firefox) встраивание на чужой домен всё равно не пропустят — там остаётся прямая ссылка |
| Журнал | таблица только на добавление, изменение и удаление запрещены триггером БД |

## Секреты

Учётные данные камер и TOTP-секреты зашифрованы libsodium SecretBox
(XSalsa20-Poly1305). Ключ — отдельный файл, монтируется docker secret'ом,
в базе не хранится. Дамп базы без ключа бесполезен.

Пароль камеры не показывается в интерфейсе никогда: в карточке видны только
хост и порт. Из сообщений ffmpeg и ffprobe учётные данные вырезаются перед
записью в лог.

Ротация ключа: `python -m app.cli rotate-key`.

## SSRF

Оператор вводит произвольный RTSP-URL, и сервер идёт по нему сам. Без
проверок это сканер внутренней сети и способ достать метаданные облака.

Что делается:

* имя резолвится, и **все** полученные адреса должны быть публично
  маршрутизируемыми (`is_global`, что закрывает и приватные сети, и loopback,
  и CGNAT `100.64.0.0/10`, и `169.254.169.254`, и документационные диапазоны);
  multicast исключается отдельно, так как для IPv4 `is_global` его пропускает;
* разрешены только схемы `rtsp://` и `rtsps://`;
* строка URL проходит фильтр символов: пробелы, кавычки, обратный слэш и
  управляющие символы отклоняются. Это важно не «на всякий случай»: при
  профиле transcode URL попадает в аргументы ffmpeg, который запускает
  MediaMTX, и пробел там означал бы подмену аргументов команды.

Исключения задаются явно: `ALLOW_PRIVATE_CAMERA_HOSTS=true` целиком либо
`CAMERA_HOST_ALLOWLIST` для конкретных подсетей.

Та же проверка применяется к управлению обзором: PTZ ходит на камеру обычным
HTTP, и адрес проверяется той же функцией (`assert_reachable_host`), а не её
копией. Результат кэшируется на 5 минут — DNS-запрос на каждое нажатие
стрелки был бы неприемлем, а не проверять вовсе нельзя.

## Управление обзором (PTZ)

Пульт добавляет сервису то, чего у него раньше не было: исходящие
HTTP-запросы к камере по её управляющему порту.

* **Отдельного поля «адрес для управления» нет намеренно.** PTZ всегда идёт
  на `camera.host` — тот самый адрес, что уже прошёл проверку при добавлении
  камеры. Настраивается только порт. Иначе появился бы способ отправить
  сервер на произвольный хост в обход всей защиты выше.
* **Учётные данные** по умолчанию берутся из RTSP-ссылки. Отдельные логин и
  пароль (нужны, когда под ONVIF заведён свой пользователь) шифруются тем же
  SecretBox и тем же ключом, что и креды камер, и в форму не возвращаются.
  Ротация ключа (`python -m app.cli rotate-key`) их перешифровывает.
* **Пароль по сети открытым не идёт.** Используется только HTTP Digest либо
  ONVIF UsernameToken (SHA-1 с nonce). Если камера предлагает единственно
  Basic, а HTTPS не включён, сервис отказывается: base64 — не шифрование.
  Такой камере нужно включить HTTPS в её собственном веб-интерфейсе.
* **Сертификаты камер не проверяются** (`verify=False`). У IP-камеры он почти
  всегда самоподписанный и выписан на адрес, которого нет ни в одном списке
  доверия, — проверять его не по чему. Выбор здесь между «без проверки
  цепочки» и «PTZ по HTTPS не работает никогда». Пароль при этом защищён
  дайджестом, а не самим TLS.
* **Редиректы не выполняются** (`follow_redirects=False`): ответ `302` от
  камеры — это способ увести запрос с проверенного адреса.
* **Право на управление** складывается из двух независимых условий:
  `Camera.ptz_enabled` (оператор настроил камеру) и `ShareLink.ptz_allowed`
  (владелец отметил это у конкретной ссылки). Галочка на ссылке не может
  включить PTZ там, где его нет, — подделанная форма не даёт больше, чем
  показывает панель.
* **Зритель по ссылке не передаёт токен** в командах пульта: право берётся из
  того же гранта в Redis, которым живут медиа-запросы. Отзыв ссылки убирает
  грант, и следующая же команда получает отказ.
* **Межсайтовый вызов** закрыт двумя условиями сразу: тело идёт как JSON, что
  требует preflight; обязателен заголовок `X-Requested-With`, который чужая
  страница без preflight не поставит. CORS не разрешён нигде, поэтому
  preflight не проходит и запрос до сервиса не доходит. На `SameSite` здесь
  не рассчитываем: cookie доступа помечена `SameSite=None` ради встраивания
  в чужой сайт.
* **Одновременное управление** невозможно: камера закрепляется за первым
  нажавшим на `PTZ_HOLD_SECONDS`. Идентификатор зрителя в Redis не попадает —
  только его хеш.
* **В журнал пишется сеанс управления, а не нажатие** (не чаще раза в пять
  минут на пару камера+человек), иначе одна наводка давала бы десятки строк.

**Остаточный риск — DNS rebinding:** между нашей проверкой и подключением
MediaMTX имя может переехать на приватный адрес. Закрывается правилами
egress на хосте, например:

```bash
sudo iptables -I DOCKER-USER -s 172.28.20.0/24 -d 10.0.0.0/8 -j DROP
sudo iptables -I DOCKER-USER -s 172.28.20.0/24 -d 192.168.0.0/16 -j DROP
sudo iptables -I DOCKER-USER -s 172.28.20.0/24 -d 169.254.0.0/16 -j DROP
```

## Чеклист перед выпуском в прод

- [ ] `nmap -sS -sU <ip>` показывает только 22, 80, 443 и 8189 (udp+tcp)
- [ ] `http://<ip>:8888/` и `http://<ip>:8889/` — connection refused
- [ ] `curl https://<домен>/metrics` и `/readyz` возвращают 404
- [ ] `/hls/...` и `/whep/...` без cookie → 403
- [ ] после «Отозвать» ссылка перестаёт работать в пределах секунды
- [ ] в HTML и JSON ответах панели нет строк `rtsp://` с паролем
- [ ] попытка добавить камеру `rtsp://127.0.0.1/`, `rtsp://10.0.0.1/`,
      `rtsp://169.254.169.254/` отклоняется
- [ ] повторный ввод того же TOTP-кода отклоняется
- [ ] при `TOTP_POLICY=all` вход без второго фактора невозможен
- [ ] `secrets/app_key` имеет права 600 и скопирован в менеджер паролей
- [ ] бэкап восстановлен на тестовом стенде хотя бы раз
- [ ] оценка A на securityheaders.com
- [ ] ZAP baseline scan по панели без находок уровня High

## Обновления

```bash
docker compose run --rm --no-deps api pip-audit
```

Образы запинены по тегу. Раз в месяц: пересобрать (`docker compose build
--pull`), прогнать `pip-audit` и `trivy image rtspgw-api:local`, сверить
конфиг MediaMTX с новым тегом.
